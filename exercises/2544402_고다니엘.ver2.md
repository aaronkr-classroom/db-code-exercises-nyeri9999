# 프로젝트 보고서

### 한국교통대학교 소프트웨어학과 2544402 고다니엘

## 1. 프로젝트 개요
본 프로젝트는 국내 관광 여행사를 대상으로 한 데이터베이스를 PostgreSQL에서 구현하는 것을 목표로 한다. PDF에 제시된 내부 스키마 정의와 인덱스 정의서를 기반으로 테이블을 생성하고, 각 테이블에 기본키, 외래키, 기본값 등의 제약조건을 적용하였다.

필수 구현 테이블로는 고객 정보를 저장하는 `customer`, 직원 정보를 저장하는 `staff`, 여행상품 정보를 저장하는 `tour`, 예약 정보를 저장하는 `reserve`, 고객 등급 코드를 관리하는 `class_code`, 직원 업무 코드를 관리하는 `task_code`를 구현하였다.

또한 **보너스 구현** 항목으로 운전기사 정보를 저장하는 `driver`, 관광버스 정보를 저장하는 `tour_bus`, 여행상품별 운전기사 배정 정보를 저장하는 `assign_driver`, 여행상품별 차량 배정 정보를 저장하는 `assign_bus` 테이블을 추가로 구현하였다.

## 2. 구현 테이블 목록(보너스 포함)

* `customer`: 고객 ID, 이름, 휴대폰 번호, 주소, 고객 등급 코드 정보를 저장한다.
* `staff`: 직원 사번, 이름, 생년월일, 연락처, 급여, 담당업무 코드, 입사일 정보를 저장한다.
* `tour`: 여행번호, 출발지, 도착지, 프로그램, 시작일시, 종료일시, 최소출발인원, 최대인원, 여행경비, 예약금, 출발여부, 담당직원사번 정보를 저장한다.
* `reserve`: 고객 ID와 여행번호를 기준으로 예약일자, 예약금 결제 여부, 여행경비 결제 여부를 저장한다.
* `class_code`: 고객 등급 코드와 등급명, 기준 정보를 저장한다.
* `task_code`: 직원 업무 코드와 업무명을 저장한다.
* `driver`: 운전기사 ID, 이름, 생년월일, 휴대폰 번호, 시급, 계약일, 계약기간 정보를 저장한다.
* `tour_bus`: 관광버스 차량번호, 좌석수, 출고년도 정보를 저장한다.
* `assign_driver`: 여행상품별로 배정된 운전기사와 근무시간을 저장한다.
* `assign_bus`: 여행상품별로 배정된 관광버스 정보를 저장한다.

## 3. 주요 제약조건

각 테이블에는 데이터를 고유하게 식별하기 위해 `PRIMARY KEY`를 설정하였다. `customer`는 `cus_id`, `staff`는 `staff_id`, `tour`는 `tour_num`, `class_code`와 `task_code`는 `code`를 기본키로 사용하였다. `reserve`는 고객과 여행상품의 조합으로 예약을 식별하므로 `cus_id`, `tour_num`을 복합 기본키로 설정하였다.

테이블 간 관계를 표현하기 위해 `FOREIGN KEY`도 설정하였다. `customer`는 `class_code`를 참조하여 고객 등급을 관리하고, `staff`는 `task_code`를 참조하여 담당업무를 관리한다. `tour`는 담당직원사번을 통해 `staff`를 참조한다. `reserve`는 예약 고객과 여행상품을 연결하기 위해 `customer`와 `tour`를 참조한다.

보너스 테이블에서는 `assign_driver`가 `tour`와 `driver`를 참조하고, `assign_bus`가 `tour`와 `tour_bus`를 참조하도록 구성하였다. 이를 통해 하나의 여행상품에 운전기사와 관광버스를 배정할 수 있도록 하였다.

기본값은 명세에 따라 고객 등급 코드, 출발 여부, 예약일자, 예약금 결제 여부, 여행경비 결제 여부 등에 적용하였다. 예를 들어 고객 등급 코드는 기본값을 `3`으로 설정하여 별도 입력이 없을 경우 일반 고객으로 저장되도록 하였고, 예약일자는 `CURRENT_DATE`를 사용하여 입력 시점의 날짜가 자동 저장되도록 하였다.

## 4. 인덱스 구현

인덱스는 PDF의 인덱스 정의서를 기준으로 구현하였다.

`tour_arrival_idx`는 `tour` 테이블의 `arrival` 컬럼에 생성하였다. 여행상품 검색 시 도착지를 조건으로 조회하는 경우가 많을 수 있으므로, 도착지 검색 성능을 향상시키기 위한 목적이다.

`driver_name_idx`는 `driver` 테이블의 `name` 컬럼에 생성하였다. 운전기사 이름은 검색 조건이나 정렬 조건으로 사용될 수 있으므로, 이름 기반 조회 및 정렬 성능을 개선하기 위해 인덱스를 생성하였다.

## 5. 테스트 결과

1. 고객 등급 검색 기능: 정상 동작
```sql
SELECT c.name, cc.class
FROM customer c
         JOIN class_code cc ON c.c_code = cc.code
WHERE c.cus_id = 'CUST001';
```

2. 직원 담당업무 검색 기능: 정상 동작
```sql
SELECT s.name, tc.task
FROM staff s
         JOIN task_code tc ON s.t_code = tc.code
WHERE s.staff_id = 10001;
```

3. 여행상품 예약 고객 검색 기능: 정상 동작
```sql
SELECT c.name, r.res_date, r.dep_yn
FROM reserve r
         JOIN customer c ON r.cus_id = c.cus_id
WHERE r.tour_num = 'TOUR0001';
```

4. 여행상품 배정 운전기사 검색 기능: 정상 동작
```sql
SELECT t.departure, d.name, d.cell
FROM tour t
         JOIN assign_driver ad ON t.tour_num = ad.tour_num
         JOIN driver d ON ad.driver_id = d.driver_id
WHERE t.tour_num = 'TOUR0001';
```

5. 신규 고객 등록 기능: 정상 동작
```sql
INSERT INTO customer (cus_id, name, cell)
VALUES ('CUST006', '신나래', '010-7777-7777');

SELECT c.cus_id, c.name, c.cell, cc.class
FROM customer c
         JOIN class_code cc ON c.c_code = cc.code
WHERE c.cus_id = 'CUST006';
```

6. 직원 급여 수정 기능: 정상 동작
```sql
SELECT staff_id, name, salary
FROM staff
WHERE staff_id = 10001;

UPDATE staff
SET salary = salary + 200000
WHERE staff_id = 10001;

SELECT staff_id, name, salary
FROM staff
WHERE staff_id = 10001;
```

7. 예약 정보 삭제 기능: 정상 동작
```sql
SELECT *
FROM reserve
WHERE cus_id = 'CUST002'
  AND tour_num = 'TOUR0001';

DELETE FROM reserve
WHERE cus_id = 'CUST002'
  AND tour_num = 'TOUR0001';

SELECT *
FROM reserve
WHERE cus_id = 'CUST002'
  AND tour_num = 'TOUR0001';
```
## 7. 프로젝트 회고문

### 1. 가장 어려웠던 SQL 문은 무엇인가?

JOIN 문이 가장 어려웠다. 여행상품 배정 운전기사 조회하는 부분에서 상당히 애를 먹어서 LLM 도움도 조금 받았다. 

처음에는 여행상품 번호를 조회하면 바로 운전기사 정보가 조회될 것이라고 생각했는데, 막상 테스트해보니 안 나와서 다시 생성했던 테이블 구조를 한참 들여다보았다. 생각하다 보니 매핑 테이블인 assign_driver를 통해서 여행상품번호와 기사의 ID를 연결해야 한다는 것을 까먹었다. 

이 과정에서 단순 테이블 생성할 것이 아니라 관계를 잘 이해하고 있어야 이런 실수를 줄일 수 있겠다라는 생각과, 이런 부분을 글로 좀 정리를 해두고 하면 나중에 참고하기도 좋겠다는 생각이 들었다.

### 2. 어떤 오류가 발생했는가?

데이터 삽입 과정에서 외래키 제약조건 오류가 발생했다. 

예시로 주셨던 sql 코드에도 class_code와 task_code를 먼저 생성했었기도 하고 이미 있어서, 깜빡하고 아무 생각 없이 customer와 staff 등의 주요 테이블에 데이터를 삽입한 다음에 아래에다가 코드 테이블 데이터를 삽입하려고 했었다.

하지만 `customer` 테이블의 `c_code`는 `class_code(code)`를 참조하고, `staff` 테이블의 `t_code`는 `task_code(code)`를 참조하도록 외래키가 설정되어 있었기 때문에, `customer`에 고객 등급 코드 값을 넣거나 `staff`에 담당업무 코드 값을 넣을 때, 참조 대상 코드가 아직 `class_code`, `task_code` 테이블에 존재하지 않아서 오류가 발생했다.

예를 들면 `customer`에 `c_code = 3`인 고객을 먼저 삽입하려고 했지만, `class_code` 테이블에 코드 `3`이 아직 등록되어 있지 않아서 외래키 제약조건을 위반하였다. `staff`도 마찬가지로 `t_code = 1` 또는 `t_code = 2` 같은 값을 먼저 삽입했지만, `task_code` 테이블에 해당 코드가 없어서 삽입이 실패하는 것이다.

이 오류를 통해 외래키를 사용하는 테이블에서는 참조되는 부모 테이블의 데이터가 먼저 존재해야 한다는 점을 확인하게 되었다.

### 3. 어떻게 해결했는가?

오류를 해결하기 위해 가장 간단하게 데이터 삽입 순서를 변경하였다. 먼저 코드값을 관리하는 부모 테이블인 `class_code`, `task_code`에 데이터를 삽입한 다음에 이 테이블을 참조하는 `customer`, `staff` 테이블에 데이터를 삽입하도록 순서를 수정하였다.

```sql
INSERT INTO class_code VALUES (1, '최우수', '우수 고객 등급');
INSERT INTO class_code VALUES (2, '우수', '일반보다 높은 고객 등급');
INSERT INTO class_code VALUES (3, '일반', '기본 고객 등급');

INSERT INTO task_code VALUES (1, '여행상품관리');
INSERT INTO task_code VALUES (2, '예약관리');
INSERT INTO task_code VALUES (3, '관광버스배치관리');
INSERT INTO task_code VALUES (4, '직원관리');
INSERT INTO task_code VALUES (5, '고객관리');
```

그 다음에 고객 테이블과 직원 테이블에 데이터를 삽입하니 정상적으로 데이터가 들어갔고, 위를 통해서 데이터 삽입 순서도 엄청 중요하다는 것을 다시 한번 상기하게 되었다.


### 4. AI 도구를 사용했다면 어떤 도움을 받았는가?

PDF 내에는 문법이 우리가 사용하는 PostgreSQL과 달라서, 어떻게 변환하는 게 좋을지 방향성 부분에 있어서 도움을 받았다.

인덱스 정의서 보고 생성하려니 막막했는데, 그 부분도 도움을 받아서 잘 작성하게 되었다.

그리고 테스트 쿼리 부분에서 JOIN QUERY와 UPDATE, DELETE 쿼리 부분들도 문법이 틀리는 경우가 있었어서 그런 부분에 대해서 오류를 수정하는 도움을 받았다.

그리고 이 보고서를 쓰면서도 글의 첨삭 부분에서 도움을 받고 있다.

### 5. 이번 프로젝트를 통해 배운 점은 무엇인가?

이번 프로젝트를 통해 데이터베이스 설계는 단순히 테이블을 만드는 작업이 아니라 테이블 간 관계와 데이터 삽입 순서까지 함께 고려해야 한다는 점을 배웠다. 특히 **외래키 제약조건이 있으면 부모 데이터가 먼저 존재**해야 하며, 삭제할 때는 **자식 데이터부터 삭제**해야 한다는 점을 실제 오류를 통해 확인(DROP TABLE 부분)할 수 있었다.

또한 `JOIN`의 필요성을 이해할 수 있었다. 고객 등급 검색은 `customer`와 `class_code`, 직원 담당업무 검색은 `staff`와 `task_code`, 예약 고객 검색은 `reserve`와 `customer`, 배정 운전기사 검색은 `tour`, `assign_driver`, `driver`를 연결해야 했다. 이를 통해 정규화된 테이블 구조에서는 하나의 기능을 구현하기 위해 여러 테이블을 조합해서 조회해야 한다는 점을 배웠다.

마지막으로 인덱스의 역할도 확인했다. 사실 인덱스는 잘 사용해본 적이 없어서 생소했는데, 인덱스를 생성하여 활용하면 조회 성능을 개선할 수 있다는 점을 배웠다. 

이번 프로젝트를 통해 테이블 생성, 제약조건 설정, 데이터 삽입, 조회, 수정, 삭제, 인덱스 생성까지 데이터베이스 구현의 전체 흐름을 실습할 수 있었다.
